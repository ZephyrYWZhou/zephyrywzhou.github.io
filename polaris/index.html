An AWS-native, serverless storage backend

Initiated & designedEnd-to-end ownerIn progress

Polaris stores catalog metadata (tables, namespaces, and access grants) in a database. Teams on AWS had to run Postgres or MongoDB just for that. I proposed a DynamoDB backend, wrote the design, earned community endorsement, and I'm building it end to end.

  • For users: fully serverless, auto-scaling, with built-in high availability and no database to run.
  • Thin adapter: reuses Polaris's existing compare-and-set model. Catalog API and entity model stay unchanged. Opt-in, no migration.
  • Single-table design: typed items by sort key, a name-sentinel item for uniqueness, and sparse indexes for listing and grants.
  • Correct by design: every correctness read is a strongly consistent single-key read. Indexes are used only for discovery.

A cleaner authorization path

3 merged PRsCore

Every catalog call runs a permission check. That logic was repeated across authorizers. I reworked it into one explicit, shared path.

  • Unified intent-to-path resolution across 3 authorizers: Polaris built-in, Apache Ranger, and OPA.
  • Threaded a typed resolved intent through privilege checks, so each check works on resolved data.
  • Removed redundant per-record overrides across 12 files of authorization intents.

One source of truth for logs

Shipped in Polaris 1.7.0

Log keys were typed as loose strings all over the code. That makes logs hard to search and easy to break.

  • Introduced StructuredLogKeys: about 55 shared keys for SLF4J structured logging.
  • Replaced about 100 hardcoded key strings across the codebase.
  • Follow-up: standardized the view-identifier key on mismatch errors.

Federation docs

Docs

Documented ENABLE_SUB_CATALOG_RBAC_FOR_FEDERATED_CATALOGS, which controls fine-grained access inside federated catalogs. It helps operators turn it on safely.
